# AGENTS.md

This file provides guidance to coding agents working with code in this repository.

## Status

The workspace, contract, API, SQLite persistence, validated Socket.IO transport, authenticated admin surfaces, design-complete web screens, and end-to-end mediasoup audio are implemented. The Expo app at `apps/mobile` is a working listener: one socket per event supplies live channel state to both public screens and both sheets, a mediasoup consumer supplies the audio, and the platform's own media controls carry it while the screen is locked. Its speaker studio is not built. The client logic both apps share lives in `packages/client-core`. Media uses a worker pool and one router per active event; guests keep one connection for the event. Two interpreters sharing a channel's speaker code swap through a negotiated handover rather than a takeover: the claim is taken by going live, moved only by agreement or after a 30-second countdown, and the swap overlaps both producers so listeners cross over without a gap. Mobile appearance is stored locally; listener volume and output follow the system. Other settings storage remains unresolved.

Keep this file current as decisions are made.

## Layout and commands

- `packages/contract` — hand-written Zod schemas and `createRoute()` definitions. Never built: every export points at TypeScript source and consumers compile it. `src/socket` holds the socket event contract behind the `./socket` subpath export and is **not** re-exported from the root barrel, which pulls in Hono via `./openapi`; browser clients import `@linguacast/contract/socket`. `src/schemas/patterns.ts` holds the bare regexes (`PIN_PATTERN`, `SLUG_PATTERN`, `SEMVER_PATTERN`), the three drawn password rules (`PASSWORD_MIN_LENGTH`, `PASSWORD_NUMBER_PATTERN`, `PASSWORD_SPECIAL_PATTERN`) and the separate request-size ceiling (`PASSWORD_MAX_LENGTH`) behind `./patterns` on the same terms — one source for the server's setup schema and the web's live validation. `src/page-titles.ts` likewise sits behind `./page-titles`, keeping public event/channel browser titles identical between initial HTML and SPA navigation without pulling Hono into the browser. The maximum is not a fourth checklist line. A space counts as the special character: refusing it would reject a passphrase while accepting `password9!`. The contract imports neither `socket.io` nor mediasoup. Its tsconfig sets `"types": []` with no DOM (the React Native seam): a `node:` or DOM import in `src` must fail to compile.
- `tools/openapi-codegen` — a private package whose only job is holding `typescript@5.9.3` and exposing an `openapi-codegen` bin; `packages/contract` depends on it. Every real package pins `typescript@7.0.2`, and TypeScript 5 must remain unreachable as a binary from any package that compiles source — `pnpm why -r typescript` is the mechanical check. Reasoning and exit condition: `docs/solutions/architecture-patterns/isolate-a-legacy-compiler-behind-a-codegen-tool-package.md`.
- `packages/client-core` — the platform-free client tier both apps consume as TypeScript source, on the same terms as `packages/contract`: no build step, no `dist`, subpath exports (`./socket`, `./channel`, `./media`, `./server`, `./query-retry`), and Metro and Vite each transpile it. The boundary is **"no platform"**: no DOM library, no React Native import, no `expo-*` package and no mediasoup-client, enforced by `test/boundary.test.ts` — a source scan in the shape of `apps/server/src/core/boundary.test.ts` that also fails on a bare `window`, `document`, `navigator` or `localStorage`. That scan reads the filesystem, so it sits in `test/` under its own tsconfig setting `"types": ["node"]`, because the package's own sets `"types": []`; `typecheck` is therefore two invocations, the arrangement `packages/contract/scripts` already uses against the identical collision. React is a **peer** dependency, and pnpm links one copy of it: `react` and `@types/react` must stay at one version across `apps/web` and `apps/mobile`, or Metro resolves a second React from inside the package and the first hook it exports throws an invalid-hook-call. `dependenciesMeta.injected` is the usual pnpm answer to that and is rejected — it hard-copies the package at install time, which is the build step this package exists without. What stayed behind is what is coupled to one platform's media APIs: the mediasoup shells, the capture layer and the audio-session hooks each live in the app that owns them.
- `apps/server` — Hono + `@hono/zod-openapi`. `app.ts` builds the app without listening; `index.ts` owns the listener. `defaultHook` must be passed to *every* `OpenAPIHono` instance that registers routes — it is not inherited by sub-apps.
- The production SPA keeps every Vite output file static except `index.html`. `http/spa.routes.ts` reads that file once at boot, requires the single `linguacast:metadata` marker pair from `apps/web/index.html`, and replaces only its four escaped title/description tags. Exact event and channel URLs get indexed SQLite lookups plus event, listener or speaker metadata; missing/disabled events and channels return the same shell with 404, and a stale non-empty speaker code returns it with 403. The speaker code is compared, never rendered. After React takes over, both public route components call `useDocumentTitle` with the same contract formatters; leaving them resets the tab to `LinguaCast`. These page lookups share the API's public rate-limit buckets, so an invalid browser navigation costs one token for the document and another when the SPA performs its API lookup. Every rendered shell is `no-cache`; real `/assets/*` files remain immutable. A missing web build is normal development configuration, while a present build with no usable index is fatal.
- `apps/server/src` is split by dependency direction. `core/` is the domain: it must not import `hono`, `@hono/zod-openapi` or `socket.io`, and must not reach sideways into `http/` or `socket/`, but it may import `drizzle-orm`, `better-sqlite3` and later `mediasoup`. `http/` holds every Hono-coupled module; `socket/` every Socket.IO-coupled one, split into `socket/lib/` for plumbing and `socket/handlers/` for per-feature events. `lib/` is what has neither domain knowledge nor transport coupling — `problem.ts`, `rate-limit.ts`, `semver.ts`. `db/` keeps its own conventions. The boundary is enforced by `core/boundary.test.ts`, a source-text scan that fails on a forbidden specifier, relative paths included: `docs/solutions/architecture-patterns/guard-a-layer-boundary-with-a-self-testing-import-scan.md`. File a module by what it is, not by the directory its only consumer occupies.
- Directories name the role; filenames name the entity plus a role suffix — `.service.ts`, `.mapper.ts`, `.routes.ts`, `.middleware.ts`, `.handlers.ts`. A module whose stem is already unique and role-descriptive takes no suffix: `codes.ts`, `access.ts`, `presence.ts`, `handshake.ts`, `on.ts`, `rooms.ts`, `types.ts`. Tests stay colocated as `<module>.test.ts`.
- `core/media/` holds the mediasoup layer: `config.ts` (codecs, listen infos, ICE servers, candidate augmentation), `workers.ts` (the pool), `room.ts` and `peer.ts`, `registry.ts` (one room per event, its creation slot and idle teardown), `announced-address.ts` (the announced address, resolved and kept current), `reflexive-address.ts` (a boot-time STUN binding request, for the cross-check alone), and `index.ts`, the facade every caller uses. It is a module singleton started by `startMedia()`, reached by import like `db` and never injected. `testing.ts` there starts it on fake workers so a test can drive it without binding a port.
- `core/auth/` is the account: `password.ts` (scrypt, self-describing hashes, a dummy hash for the unknown-username path, and a semaphore bounding how many 32 MB derivations run at once), `credentials.ts` (`admin.json`, an atomic write, a strict parse), `account.ts` (the module singleton started by `startAuth()`, in the shape of `core/media`), `sessions.ts` (the `admin_sessions` table) and `index.ts`, the facade. Credentials live in `admin.json` beside the database and nowhere else — never in SQLite, never in a config file a human edits — so recovery is deleting one file in the directory the operator already mounts and restarting. The file is read once at boot and held in memory: a running server cannot become unconfigured, and a file that exists but does not parse is fatal rather than silently unconfigured, which would re-open the account-claim window after a disk glitch. `createAccount` takes its claim synchronously before it hashes, for the same reason `authorizeHandshake` stays synchronous. `resetAuth()` performs the recovery in process; it exists so a test can drive a server from configured back to unconfigured.
- Sessions are rows keyed on a SHA-256 of the token, never the token: a copied database must not yield live sessions. 30 days, renewed on use only inside the last day of that life, swept at boot and deleted wherever a lookup finds one expired. The cookie is `__Host-linguacast_session` — the prefix has to be supplied at all three call sites in `http/session-cookie.ts` or the name will not match — httpOnly, `SameSite=Lax`, and `Secure` unconditionally, since `getUserMedia` already requires HTTPS.
- Auth endpoints are `/auth/*`, deliberately outside `/admin`: sign-in cannot sit behind the prefix it exists to unlock. `http/middleware/require-admin.middleware.ts` is the one `app.use('/admin/*', …)` that prefix exists for, and it checks that an account exists *before* it checks the session — between a recovery restart and the finished wizard the table still holds rows corresponding to no account. Refusals are a `Problem` with 401 and never a redirect: the caller is `fetch`, and the SPA turns the 401 into a route guard.
- Sign-in is throttled per address and never locked out. `createRateLimit` takes the statuses that cost a token (404 for the public limiter, 401 and 409 for sign-in) and the sign-in limiter has **no** shared global budget behind it: against a single account a shared budget is a lockout, because the budget check runs before the handler and a distributed guesser holding it at zero refuses the correct password too. What that budget protected — many concurrent scrypt allocations — is bounded by the semaphore in `password.ts`, which makes a caller wait rather than fail. `clientIp` trusts the rightmost `X-Forwarded-For` entry only from an address listed in `TRUSTED_PROXY_IPS`, the one environment variable this work adds; unset means the header is never believed.
- The web learns its state from one unauthenticated `GET /auth/session` (`lib/auth-queries.ts`), read by `beforeLoad` on `/`, `/admin`, `/setup` and `/login`. A 401 from any admin call invalidates that entry and then the router, so a dead session produces one redirect rather than a five-second poll failing forever; `/auth/*` is excluded, because a wrong password is not a dead session. After setup and after sign-in the entry is **seeded from the response**, not invalidated: `ensureQueryData` hands back the stale value while a refetch is in flight, and the stale value says signed out. The attempted path is carried in `?redirect=` and accepted back only as an internal router path.
- A server test file must reach `core/auth` **only** through `createTestApi()`, which returns `signInAsAdmin`, `createSession`, `resetAuth` and `SESSION_TTL_MS` from its own dynamic import. A static `import … from '../core/auth'` anywhere in a test file's graph loads `env.ts` before `createTestApi` can set `DATA_DIR`, so `credentialsPath()` resolves against the real `./data/` — the suite then provisions the operator's database and `resetAuth()` deletes their real `admin.json`. `createTestApi` passes an explicit `admin.json` path to `startAuth()` for the same reason. This is what the file's own comment about dynamic imports has always been protecting, extended to the credential file.
- Only `isOnline` moved out of `core/presence.ts`, not the whole registry: the registry also tracks every connected studio socket per channel, which exists before any media does. The claim means broadcast rights; `isOnline` means an unclosed producer exists. The claim is keyed on a **studio session** — an opaque id a studio page generates once and holds in memory — so a studio's own reconnect is told apart from a colleague's studio presenting the same speaker code, a reload is a different studio, and `release` by a socket the same session has already replaced is a no-op in either arrival order. It is taken by `take` at go-live, moved only by `core/handover.ts`'s promotion, and every transition publishes one `claim-changed` notification. It also carries the moment the channel went on air, which a rebind and a move both inherit — including a move after the outgoing holder's socket dropped the claim — and only a release with nobody waiting resets: the broadcast belongs to the channel rather than to one interpreter, so the studio's elapsed timer continues across a handover instead of restarting. It reaches the studio as `onAirMs` on the handover snapshot, a duration anchored at receipt like everything else on that message, and deliberately not on `ChannelStatus` — no guest surface may state how long a channel has been on air.
- `core/reports.ts` is the rolling per-channel tally of listener issue reports: five fixed problem categories in a five-minute window, a separate positive `Audio sounds good now` tally in a 30-second window, a two-minute per-socket category cooldown, and one unref'd timer per channel armed at the next expiry across both windows so the studio's panel empties without a client re-deriving either one. One accepted problem opens a connection-scoped feedback episode; its positive follow-up clears that connection's active problem entries but retains their hidden timestamps until the cooldown passes, and the episode remains resolvable after the visible problems expire. Confirmation, disconnect, or a deliberate broadcast end closes the episode. The positive signal is not a sixth problem category and never claims every listener is fixed. The registry sits beside `presence.ts` rather than under `core/media/` for the same reason presence does — a report is about a channel and the registry must be reachable whether or not a room exists — and it is process memory, never SQLite: a stored report is a record about an audience that has no account. Cooldown and resolution eligibility bound a connection rather than a person; a reload is a new socket. That is the accepted limit, not a gap to close: an address key would silence every listener behind one NAT, and a listener-generated identifier is the identity this product does not have.
- Events originating inside `core/` reach clients through `core/notifications.ts` — a typed subscribe registry over a discriminated union, at `core/` rather than `core/media/` because regenerating a PIN must evict listeners who own no media at all. `socket/index.ts` is its only subscriber and the only place that turns an eviction into a disconnect. `EvictionReason` is `worker_died` or `access_revoked` and nothing else: a handover disconnects nobody, so there is no takeover reason. Revoking a channel evicts **every** studio socket on it rather than only the one on air — they all hold the code that was just revoked, and one left in pre-flight could otherwise still go live on it. Named notifications, not events: `core/events.service.ts` already means the domain entity. Nothing is injected into `core/`, and no handler registry maps event names to handlers as data.
- `apps/web` — Vite 8 + React 19 SPA. TanStack Router with file-based routing: a file under `src/routes/` *is* a route, and the Vite plugin regenerates `src/routeTree.gen.ts` on dev-server startup and on every change there. Nest routes as directories, not dotted filenames — `routes/admin/events/$id.tsx` — and a directory's layout route is its `route.tsx`. `routeTree.gen.ts` is generated, committed, and excluded from Biome. `tsconfig.json` must not declare `baseUrl`; TypeScript 7 removed it, and `paths` alone resolves for both `tsc` and the shadcn CLI. `src/socket` lifted into `packages/client-core` and is gone from here; `src/state` was an empty directory and went with it. `src/api` stayed web-only, and the prediction that it would move was half wrong: it hardcodes a same-origin base path and sends credentials, while the mobile client takes its host from the route and has no session — the two share a shape rather than a module. Everything else under `apps/web/src` is web-only. `src/lib/socket.ts` exports `connectSocket(auth)`, not a module singleton: the handshake carries the event's PIN, so one socket per page is required.
- `src/components/ui` is the shadcn CLI's target: add and update components with `pnpm dlx shadcn@latest add <name>` from `apps/web`, then `pnpm check:fix`. Deliberate customisations are allowed there but each must be recorded in this list, because a later `add` silently drops it. Current customisations: `button.tsx` carries a `pill` size (`h-12 rounded-full px-6 text-base font-semibold`) plus the admin action scale — `action`, `action-sm` and `icon-action`; `switch.tsx` checks to `foreground` and carries a `tone` prop that opts back into `primary`, plus an `lg` size (46×27 with a 21px thumb, its padding and checked offset written out because the CLI's `calc(100%-2px)` only centres the thumb at the default size's proportions); `input.tsx` carries a `shape` variant defaulting to `pill`; `dialog.tsx`'s `DialogContent` defaults to `rounded-lg p-panel` with no gap, its `DialogTitle` to `text-title` and its `DialogDescription` to `text-note`; `badge.tsx` carries a `size` variant holding the chip geometry the base used to; `button.tsx` also carries a `destructive-solid` variant, the confirming half of a destructive dialog, where `destructive` is the tint a row action carries; `select.tsx`'s trigger and `slider.tsx`'s thumb carry `cursor-pointer`; `sonner.tsx` imports `useTheme` from `@/components/theme-provider`, not `next-themes`. `card.tsx` and `label.tsx` were deleted rather than adopted: neither had an importer, and `pnpm dlx shadcn@latest add card` gets one back. The rule the list exists to enforce: **a `components/ui` default that every call site overrides is a bug, not a style** — push the product's value into the primitive and delete the constants that were cancelling it. The `rounded-[min(var(--radius-md),Npx)]` clamps on `button.tsx`'s `xs`/`sm` and `select.tsx`'s small trigger are shadcn's own spelling, are unreferenced by any app call site, and stay as they are. `add` will offer to overwrite `button.tsx` when it is pulled in as a dependency of another component (`sheet` does this) — decline that prompt. Prefer call-site classes for one-off styling. `biome.json` turns six lint rules off for that directory only (four `a11y`, `noArrayIndexKey`, `noDoubleEquals`); do not hand-fix generated files. Reasoning: `docs/solutions/conventions/customising-generated-shadcn-components.md`.
- The design's off-scale values go on the Tailwind scale, not into arbitrary utilities: the spacing scale derives from `--spacing`, so 26px is `6.5`, 18px is `4.5`, 1120px is `280`. Six values are named in `index.css`: `--spacing-gutter` (the 26px screen gutter, `px-10` from `lg`), `--spacing-shell` (the 1120px application content cap), `--spacing-panel` (the 22px panel inset), `--spacing-action-x` (17px), `--spacing-action` (38px) and `--spacing-touch` (44px). The type ramp is fifteen `--text-*` entries — `text-screen` / `text-screen-lg`, `text-hero` / `text-hero-lg`, `text-stat` / `text-stat-lg`, `text-pin` / `text-pin-lg`, `text-title`, `text-subtitle`, `text-section`, `text-body-lg`, `text-label`, `text-meta`, `text-note` — each carrying its own weight and line-height plus tracking where the design fixes one; body text is `text-sm`, and 16px, 18px and 20px are Tailwind's own `text-base`, `text-lg` and `text-xl`. There is no `text-[…]` anywhere in `apps/web/src` except shadcn's own `text-[0.8rem]` on `button.tsx`'s `sm` size; a new type size goes on the ramp or reuses a step, and near-duplicates collapse rather than earning an entry. Radius: `rounded-lg` (20px) is the panel, `rounded-md` (16px) the PIN slot, `rounded-xl` (28px) the sheet; `level-meter.tsx`'s `rounded-[1px]` peak marker is the only literal left, because one use is not a scale entry. The animations are `--animate-pulse-live`, `--animate-ring` and `--animate-ring-delayed`, all held at a resting frame under `prefers-reduced-motion` rather than removed. Where the canvas and the handoff prose disagree on an animation value, the canvas wins. Arbitrary values remain right for one-off type sizes and grid templates. Colours are never written at a call site: they are `--color-*` tokens in `index.css`, referenced by role (`text-muted-foreground`, `border-destructive`), never as a hex and never as a role borrowed to mean something else. `--live-on-muted` is the live colour *as type* on a muted surface — `live-muted` or `secondary` — and never on a `live` fill, which in dark mode is the same value. `warn` is the fourth colour, four tokens (`--warn`, `--warn-on-muted`, `--warn-muted`, `--warn-border`) built the way `live` and `destructive` are: amber is a row wash and a figure, never a solid fill and never a dot, which is what keeps it clear of `primary`, the colour of what can be pressed, and of `live`, the colour of audio moving. The canvas's `--warn-foreground` is deliberately absent — it paints only the palette demo's own swatch, and a type-on-solid-warn token would be a default with no call site. **Hover:** hover always moves toward `foreground`, in both themes, by a fixed mix — never by lowering the element's own opacity. `hover:overlay` washes a control that has a resting fill, `hover:overlay-strong` one that does not; both are `@utility` entries in `index.css` that paint the wash as a background *image*, so the control's own fill survives underneath and the result does not depend on the surface behind it. A solid `primary` fill uses `hover:bg-primary-hover` instead, which darkens in light mode and lightens in dark: `primary/80` blends toward the page and reads as disabled rather than hovered. An opacity-blended hover (`hover:bg-muted/50`, `hover:bg-card/70`) is the bug this replaces — in dark mode `muted`, `secondary`, `card` and `popover` are all one value, so a ghost control on any panel hovered to exactly the colour it already sat on. That collision is the underlying problem and the overlay routes around it rather than solving it; giving dark `--muted` its own step, the way `--accent` was already lifted one above `popover`, is a separate decision. **Focus:** a filled control takes a ring, a bare text link or a full-row link target takes a 2px outline, and the offset is 2 everywhere. **Touch targets:** a control that sits in a cluster of sibling controls bumps to 44px below `lg` and settles at 38px from `lg` — which is what `size="action"`, `"action-sm"` and `"icon-action"` do, so it comes for free. A control alone in its row does not need the bump; the named exceptions are the admin nav links and the guest back button, both sized by their surroundings rather than by the action scale. Procedure for a new value: `docs/solutions/conventions/design-values-onto-the-scale.md`.
- The studio's handover surface is `speaker/handover-prompt.tsx` and `speaker/handover-countdown.tsx`, both alert rows built on `speaker/handover-alert.tsx`, with every string it can render in `lib/handover-copy.ts` so `handover-copy.test.ts` can enumerate them and hold them to the studio's rule about claiming an audience. The prompt is a non-modal row spanning both on-air columns rather than a dialog: the interpreter is mid-sentence, and a modal would take the mute target away to ask a question that can wait for a natural break. It offers `Hand over` only — there is no decline — and the studio keeps transmitting and says it is handing over until the swap completes. The studio badge (`studioBadge` in `speaker-studio-state.ts`) reports this studio only and never names or reflects another interpreter, so pre-flight's badge always reads `Off air`. A colleague holding or receiving the channel is the warn-toned `HandoverAlert` above pre-flight's title instead. Pre-flight's `unknown` action raises no alert — the holder is unknown on every load until the first snapshot lands — and is withheld instead by the disabled `Checking…` action and a quiet note beside it; offering Go live there would put an interpreter on air over a colleague. A completed handover returns the studio to pre-flight through `use-media`'s `abandonProducer`, which drops the local sender and sends **no** `media:close-producer`: the successor owns that producer by then. `SpeakerDisplaced` is now for an organiser ending the session and nothing else.
- The setup wizard (`routes/setup.tsx`, two steps in one route) and sign-in (`routes/login.tsx`) share `components/auth/auth-card.tsx`, `password-field.tsx` and `password-checklist.tsx`; `lib/password-rules.ts` is their pure half. There is no password-change or reset surface anywhere, by design. Sign-out lives in the admin header and no account settings screen was invented ahead of the design.
- Components are filed by flow: `src/components/guest`, `src/components/speaker`, `src/components/admin`, `src/components/auth`, with everything used by more than one flow at `src/components/` root — `logo-lockup.tsx`, `PlayTarget`, `LevelMeter`, `LiveDot`, `LiveBadge` (whose `showDot={false}` is the same chip carrying a name rather than a state), `AppHeader`, `ConnectionLine`, `ConfirmDialog`, `MICRO_LABEL` (the uppercase micro-label, a class constant rather than a component because its call sites apply it to three different elements) `Pin` (a PIN shown as digits; a PIN inside a sentence keeps `formatPin` directly) and `ResponsiveSurface` (the sheet-below-`lg`, dialog-from-`lg` chrome with its grabber, title and `Done`, extracted from `AudioSurface` when the report sheet needed the same chrome behind a text-link trigger; `AudioSurface` is now that chrome composed with the settings row). The second flow that needs a component moves it to the root rather than importing across. All of it is hand-written, deliberately outside `components/ui`, and none of it is a `packages/client-core` candidate.
- One non-trivial product component per `.tsx` file. A full screen, stateful form, mutation owner, or independently reusable view gets its own named-export file even when only one parent imports it. Small private render helpers may stay with their owner; small compound families such as guest-message helpers may stay together. Generated shadcn compound primitives under `components/ui` are exempt. Do not create feature barrel files to hide the resulting direct imports.
- `src/lib/audio` is the web-only capture and playback-routing layer, not a `packages/client-core` candidate: `level.ts` owns RMS, decibel mapping, status thresholds and meter motion; `devices.ts` owns pure microphone list shaping; `preferences.ts` owns the microphone preference type, capture-constraint and gain mappings, defaults, and tolerant parse/serialize; `media-session.ts` owns pure Media Session state mapping; `use-audio-preferences.ts` owns browser storage for microphone preferences; `use-listener-media-session.ts` owns listener lock-screen metadata, Play/Pause handlers and real media-element playback state; and `use-mic-capture.ts` owns input devices, streams, and one `AudioContext`/`AnalyserNode` per stream. Media Session is best effort: it advertises active listener audio to the browser but does not guarantee that every mobile OS keeps WebRTC alive in the background. The four microphone preferences live as one `linguacast-audio-preferences` object. They are unversioned and parsed/defaulted field by field against `DEFAULT_AUDIO_PREFERENCES`. Echo cancellation defaults to and emits explicit `false`. Stored microphone values are mount-time defaults, never adopted live; writes merge field by field so another tab cannot revert untouched fields. Do not restore gain below `MIN_RESTORED_GAIN`. Browser auto gain runs before the app's `GainNode`, so enabling it forces that node to unity without discarding the stored manual gain; disabling it restores that value. Open a microphone stream before enumerating because labels are empty before permission, and collapse the browser's duplicate `default`/`communications` microphone aliases. Release capture only through the path that stops tracks and closes the context. Meter values and thresholds are positions on the `METER_FLOOR_DB`-to-full-scale decibel scale, never raw amplitude. Use `getFloatTimeDomainData`, never the 8-bit byte API. The fill uses a timestamp-driven one-pole filter (`ATTACK_MS` 20, `RELEASE_MS` 280); `levelStatus` and `data-peaking` instead use a decaying peak-hold of raw RMS (`HOLD_DECAY_MS`) so short peaks remain visible. `speaker-studio.tsx`'s `SIGNAL_POLL_MS` latch also stays raw so smoothing cannot delay Go live.
- Android browsers do not consistently promote a WebRTC `srcObject` into persistent media focus. `media-session-carrier.ts` builds a six-second unmuted digital-silence WAV and `use-media-session-carrier.ts` loops it only while listener intent is active, so Android sees qualifying file playback while real audio remains on its WebRTC element. The Media Session position duration stays `Infinity`, declaring live, non-seekable content so supporting system controls do not expose the carrier's six-second loop. Do not mute the carrier or set its volume to zero: either can prevent the audio-focus request this workaround exists to obtain. That focus is also the only way the page learns another app started playing: the browser suspends file playback when it loses focus but leaves a WebRTC `srcObject` running, classifying live communication audio as exempt, so a pause the app did not ask for is taken as the interruption and stops the listener. The carrier loops, so it never pauses on its own and every pause has one of two authors; the one the app requests is claimed before the call and only when the element is actually playing, since `pause()` on a paused element fires no event and a claim left standing would swallow the next interruption.
- Chrome's permission prompt is invisible to an agent driving the browser through the devtools MCP: a click that trips `getUserMedia` returns success and the screen never changes. Ask the human to grant it before driving the studio — `docs/solutions/workflow-issues/browser-permission-prompts-stall-the-agent-silently.md`.
- Listener counts are settled: a listener is a guest holding an open, locally unpaused consumer on the channel's producer — someone receiving audio, not someone with a page open (`Listening` in `CONCEPTS.md`). The count therefore exists on the speaker studio and on the admin event detail, and **no guest surface carries one at all** — the design's guest placeholders were removed rather than parked, and the studio's pre-flight screen shows no count and no promise of one, because the number is structurally zero before a producer exists. - `apps/mobile` — Expo SDK 57 + React Native 0.86, the iOS and Android client. `expo-router` file-based routing, so a file under `app/` *is* a route; Event and Channel are addressed by host and PIN in the path (`app/events/[host]/[pin]/[slug].tsx`) rather than by a stored record id, which is what keeps opening an event independent of the history list — a scanned code reaches Event before anything is remembered. A bare host is one path segment by construction; an origin would have been three because of its `://`. A dot inside a dynamic segment is undocumented and was verified empirically to round-trip, so `src/links/route.ts` encodes nothing — that pair of functions exists as the one place a future router version reserving the character would change. It depends on `@linguacast/contract` and never on `@linguacast/web`, and it consumes the contract as TypeScript source: Metro transpiles any file it resolves and its `package.json#exports` support has been on by default since SDK 53, so **no build step is added to `packages/contract`**. Import the subpath exports and never the root barrel, which pulls in Hono — and note that `./schemas` pulls it too, so the app uses the type-only `./openapi` for payload shapes, `./patterns` for the PIN and slug regexes, and a **type-only** import of `./socket` for the report vocabulary. `__tests__/contract-resolution.test.ts` guards that seam. It also depends on `@linguacast/client-core` on the same source-only terms, which is where the socket, channel and media decision modules now live — nothing is copied from `apps/web` any more. The app targets a **custom dev client and never Expo Go** — `expo-camera`, `expo-sqlite`, `react-native-svg`, `react-native-webrtc` and the local audio module are native — and `apps/mobile/README.md` is the contributor-facing half. Pulling these changes requires a dev client rebuild; Metro alone will not pick up a native dependency.

- The mobile listener's own layers, all of them outside `packages/client-core` because each is coupled to a platform: `src/socket/provider.tsx` owns the event's one connection and publishes the socket, the media leg, listener volume, the output route and the report episode through one context. It is a **nested route layout** (`app/events/[host]/[pin]/_layout.tsx`) rather than a per-screen hook for two reasons — a stack navigator keeps the Event screen mounted under the Channel screen, so per-screen sockets would hold two connections to one server, and the two sheets are separate routes that cannot be handed props. The sheet `Stack.Screen` entries moved into that layout with it, and it declares its own `unstable_settings.initialRouteName`: the root layout's applies to the root stack alone, so a deep link straight to a channel would otherwise leave no Event screen underneath. Every screen in that layout is declared, in the order a guest meets them and the sheet last: Expo Router hands React Navigation the explicitly declared screens before the rest, and the navigator is given no initial route name of its own, so a sheet declared first becomes the route the stack starts on and opening an event lands on the report sheet drawn full-screen. `src/media/` is the mediasoup shell — a receive-only port of `apps/web/src/lib/media/`, with the produce branch absent rather than carried as dead code, and every threshold and step decision taken from the shared media state. The handler is **named** (`ReactNative106`, annotated against mediasoup-client's own union so a renamed one fails `pnpm typecheck`), because the library's detection reads a browser user agent. `registerGlobals()` runs at app entry, before anything can construct a device. There is no page to reload when the recovery ladder gives up, so the Channel screen offers a session restart instead of the web client's `Reconnect`. `src/version.ts` derives independent mobile artifact version from `apps/mobile/package.json`; `app.config.ts` gives Expo same value. Provider fetches `/api/version` before event API or socket work and applies centralized compatibility policy from `@linguacast/client-core/server`. Returning from the background reopens a socket the operating system suspended: Socket.IO retries a transport failure it saw, and a suspension is one it did not. Two more signals join it in `use-app-state-reconnect.ts`, and none covers the others: the session heartbeat reopens a socket found disconnected, and a network change **cycles** it — a socket over the network the device has just left goes on reporting itself connected, because the ping timeout that would have told it is one of the suspended timers, so only a deliberate close makes the loss real. The media ladder reads the same heartbeat for its deadlines (`src/media/ice-clock.ts` holds the pure half) and cycles the connection when a recovery step goes unanswered past `STALLED_STEP_MS` — twelve seconds, above Socket.IO's own ack deadline so a merely slow server never trips it, and three over a transport the browser has already declared `failed`. A signalling call is skipped outright while the socket is known disconnected: a reconnect voids the server's peer state wholesale, so there is nothing left to release.
- `apps/mobile/modules/linguacast-audio` is a **local Expo module**, tracked in git and autolinked by prebuild — unlike `ios/` and `android/`, which stay generated. It owns the platform audio session, the Android media playback foreground service, the system media controls and the output route, and it exists because no maintained package displays lock-screen controls for audio it does not itself play: `react-native-track-player`'s free line has not shipped since 2025-08 and its rewrite is commercially licensed, and both own playback, which here belongs to `react-native-webrtc`. It is the **single owner** of the iOS audio session — libwebrtc's `RTCAudioSession` fights any other library that sets a category, which is why `expo-audio` is not installed at all. The category stays `playAndRecord` even though nothing here records: libwebrtc plays through a voice-processing audio unit, and that unit cannot start under a playback-only category. Measured, not assumed — `.playback` produced `AUIOClient_StartIO failed (-66637)` and a live track that made no sound, which is exactly the receive-only failure this module is defensive about. What *is* changed off libwebrtc's default is the mode and the options: the default voice-chat mode applies call processing to interpreted speech and routes to the earpiece, so the mode drops to default, `.defaultToSpeaker` moves it off the earpiece, and Bluetooth is allowed as A2DP only — permitting HFP as well would drag a headset down to call quality. The consequence to weigh before shipping: `playAndRecord` means iOS treats the app as microphone-capable, so it shows the recording indicator while a guest listens and the usage description the WebRTC config plugin writes is load-bearing rather than incidental. The session is also activated explicitly rather than left to auto-activation on track arrival. The Android service type is `mediaPlayback` and not `microphone` — this is a receive-only listener, and the wrong type invites a store review question the product cannot answer — and activation is idempotent in both directions so the 30-second playback hold can span it, because Android refuses to start a foreground service from the background. That refusal is why the session follows the guest's **request** rather than the consumer: `systemControls` withdraws on `listening` alone, so a dropped link, a reconnect and the hold all keep the session and report paused instead of stopping a service the app could not start again from a pocket. The controls' `playing` still follows the consumer. A pause holds the session for the same reason and one more — the controls are what a guest presses to resume, so withdrawing them turns Pause into Stop — and the consumer is already closed by then, so what is held is a notification rather than a stream. The cost is on iOS: `playAndRecord` means the recording indicator stays lit for as long as a guest leaves a channel paused, which is the price of keeping Play reachable. It also holds the **audio focus**, and that is the only thing that makes another app's playback and this one exclusive: a `MediaSession` is not a focus request, so an app that never asks is never told when another app starts and the two streams simply play over each other. The request is `AUDIOFOCUS_GAIN` with media attributes, claimed alongside the session and again on the way to playing — a permanent loss abandons it, so without the second claim the guest's next press resumes underneath whatever took it. It is built through `AudioManagerCompat`, taken with `setWillPauseWhenDucked(true)` — ducking interpreted speech leaves it present and unfollowable, and this app owns no volume control to duck with — and a loss is delivered as the same `onRemotePause` the lock screen sends, so the platform's pause and the guest's reach one handler. A transient loss is resumed from and a permanent one is not: the app that took the focus outright is the one the guest chose. A refused activation is retried with a capped backoff rather than logged once, and `POST_NOTIFICATIONS` is requested before the first activation — asked for, never depended on, since a guest who declines still hears the interpreter and loses only the lock-screen control. The controls offer play and pause only: every seek, skip and scrub command is disabled outright, since an enabled iOS seek command is what adds the scrubber, and the Android session reports an unknown duration, which is what withholds the bar. The module also **reads** the current output route and the device's own media volume, and emits both as events — Android has no public broadcast for either, so the outputs are watched with an `AudioDeviceCallback` and the level with a `ContentObserver`; iOS observes the route notification and the session's `outputVolume`. Reads, not writes, for the reason the next bullet gives. It also owns the listener's **recovery clock**, because the JavaScript one stops: React Native does not service timers while the app is not visible on Android, so an ICE deadline, Socket.IO's own reconnection backoff and its ack timeout are all suspended behind a locked screen — measured as ninety seconds of a dropped link where nothing at all ran. The service therefore holds a `PARTIAL_WAKE_LOCK` (a foreground service keeps the process, not the CPU, and once the audio stops nothing else holds the device awake) and emits `onTick` every two seconds, mirrored on iOS by a main-runloop `Timer` while the session is active. Beside it the module watches the **default network** — `registerDefaultNetworkCallback` on Android compared by network handle, `NWPathMonitor` on iOS compared by interface type — and emits `onNetworkChange`. That event is the cause rather than a symptom of it, and acting on it is what turns a twenty-second recovery into a two-second one; the heartbeat stays as the backstop for a drop no network change explains. Only a real change is emitted: both callbacks also fire on registration and on ordinary capability updates.
- **Remote audio plays on Android's media stream, not its call stream** — and the mechanism is not the obvious one. libwebrtc builds its `AudioTrack` with `USAGE_VOICE_COMMUNICATION`, which puts a listener under the call volume keys with a bias toward the earpiece; setting the audio manager's mode does **not** move it, measured on a device. The attributes are chosen where the track is created, so the fix is handing `react-native-webrtc` a `JavaAudioDeviceModule` built with media attributes, before React Native starts — which is what `plugins/with-media-stream-audio.js` injects into `MainApplication.onCreate`. Expo's autolinking dropped its own application lifecycle hook after SDK 56, which is why a config plugin rather than a module entry. Reading the current route follows from the same fact: `audioManager.communicationDevice` describes a routing nothing is using once the audio is on the media stream, and Android has no public call for the media route, so the connected outputs are ranked by the precedence Android itself applies.
- **The mobile app has no audio settings of its own: it states the platform's, and offers no control that would duplicate or fail.** There is no Audio sheet, no volume slider, no mute and no output picker; the Channel screen has no audio readout, and the Report sheet's self-check alone reads the device's media volume. The reason is a fork Android forces and iOS only half escapes. An app can choose the output device **only** for audio on the communication stream — `setCommunicationDevice` affects `USAGE_VOICE_COMMUNICATION` and nothing else — so the picker and the media stream cannot both be had. The media stream wins: it is what puts a listener's audio under the volume keys they already hold, keeps it off the earpiece, and spares interpreted speech the call-tuned processing. With that settled, an in-app level could only attenuate *below* the device's own, which is a second control for a job the hardware keys already do; and libwebrtc's `AudioTrack` is not reachable from outside the audio device module, so `setPreferredDevice` is not an escape either. iOS *does* have a working app-callable route picker in `AVRoutePickerView`, and it is deliberately not used: one platform having a control the other cannot is a worse product than neither having it. Do not reintroduce any of this without revisiting that fork — the per-track `_setVolume` on `react-native-webrtc` still exists and still works, and is still the wrong answer.

- Mobile's `/api/version` read gates every event request and the socket, and it is a **context**, not a wrapper that replaces the tree: `EventSocketProvider` publishes a `ServerGate` and keeps the navigator mounted through every verdict, while each public screen renders the gate's message inside its own chrome with a back action. Returning a failure in the provider's place takes the stack with it and strands a guest with no way home. A verdict is taken only from an answer the app has actually read: a refetch that fails over a server already found compatible leaves the event connected, exactly as `EventScreen` already treats its own event query. The gate's strings live in `src/socket/server-check.ts` with the other pure copy modules, enumerated and tested against the forbidden-claim list.
- `apps/server/src/db` — better-sqlite3 + Drizzle. `client.ts` holds the `createDb(path)` factory and must stay free of import side effects; `index.ts` holds the `db` singleton and opens a file at module scope. `testing.ts` imports the factory, never the singleton, or loading the test helper would provision `./data/linguacast.db` on every test run. Handlers `import { db }`; there is no dependency injection and none is wanted.
- Migrations are generated, reviewed and committed under `src/db/migrations`. Run `pnpm -F @linguacast/server db:generate` after any change to `schema.ts`, read the SQL, commit it. `drizzle-kit push` is rejected — it leaves nothing in git. There is deliberately no `db:migrate` script: `runMigrations(db)` runs in `index.ts` before `serve()`, so the operator's upgrade procedure is "pull and restart". `apps/server/src/db/migrations` is excluded from Biome — drizzle-kit rewrites its JSON metadata without a trailing newline on every generate.
- `migrate.ts` resolves its folder against `import.meta.dirname`; `DATA_DIR` resolves against the working directory. Migrations are a build artifact and travel with the bundle (`scripts/copy-migrations.mjs` places them at `dist/migrations`); the database is user data and would be destroyed by every redeploy if it lived in `dist/`.
- The four pragmas in `createDb` are all non-defaults, and `foreign_keys` is per-connection — unset, constraints are silently inert, which is why it carries a test. `data/` is gitignored, so the factory's `mkdirSync` is what makes the first `pnpm dev` on a fresh clone work.
- `better-sqlite3` is `false` in `pnpm-workspace.yaml`'s `allowBuilds`. Do not run `pnpm approve-builds` for it — `docs/solutions/integration-issues/decline-the-inferred-native-build-for-better-sqlite3.md`. `mediasoup` sits directly below it as `true`, which looks like an inconsistency and is not: its postinstall *downloads* the prebuilt worker binary rather than compiling one, so blocking it yields no worker at all instead of a slower build.
- `drizzle-zod` is deliberately absent. Row types come from `$inferSelect` / `$inferInsert`. A row is not a DTO, and API schemas are never derived from tables.
- The domain tables are `events` and `channels`. Both default to disabled; there is no lifecycle column. `pin` and `speaker_code` are regenerable natural keys and therefore never primary keys. A channel's `slug` is immutable after creation and is unique only within its event, via the composite `channels_event_id_slug_unique`. The throwaway `meta` table was dropped by migration `0001`; its `0000` migration stays in history rather than being rewritten.
- The admin events list returns each event with its channels — a `listChannels` per event. Deliberate at this deployment's scale, not an accidental N+1.
- 404 parity is a rule: a disabled event, a disabled channel and a nonexistent PIN produce byte-identical responses, enforced by a test in `http/routes/events.routes.test.ts`. The channel lookup checks existence before the speaker code. Failed public lookups are rate limited by an in-memory per-IP token bucket (burst 20, refill 1/s) with a smaller global budget behind it, charged on 404 responses only. Reasoning: `docs/solutions/conventions/identical-404s-for-disabled-and-nonexistent-resources.md`.
- `apps/server/src/testing/api.ts` sets `DATA_DIR` before *dynamically* importing `../db`. `env.ts` parses `process.env` at module load and `db/index.ts` opens a file at module scope, so a static import would provision the real `./data/linguacast.db` when the tests run.
- The socket endpoint is `path: '/api/socket.io'` on the default namespace — a path, not a namespace, so one Vite proxy rule and one reverse-proxy rule cover both the API and the socket. Socket.IO attaches at the `http.Server` level and intercepts that path before Hono sees it, which is invisible from `app.ts`.
- The handover surface is four acked client-to-server verbs — `handover:request`, `handover:cancel`, `handover:confirm`, `handover:take-over` — and one server-to-client `handover:state`. The verbs carry a **strictly empty** payload: the server reads the channel and the studio session off `socket.data`, so nothing on the wire can name a studio other than the caller (`docs/solutions/conventions/an-identifier-returned-to-a-client-is-not-a-capability.md`). The snapshot is built per studio socket, because two studios on one channel see the same facts from opposite sides; it carries `holder` (self/other/none), this studio's `role`, whether anything is `pending` on the channel at all, a `remainingMs` anchored at receipt in the shape `ChannelReports` uses `ageMs`, and `canTakeOver`, which is the server's answer and must never be re-derived from a client clock. `ChannelStatus` and the `channel:join` ack both carry `producerId` and, during a swap window, `incomingProducerId`: a replacement reaches a listener as one status naming the new producer rather than as a close followed by an open, which a single render batch could collapse into silence.
- The two report events are `channel:report` (client to server, acked) and `channel:reports` (server to client). The tally is addressed to the socket holding the channel's speaker claim, exactly as `channel:listeners` is: a room-scoped emit would hand every listening guest a number that is the interpreter's alone. Both are seeded on `claim-changed` to the socket that just acquired or rebound the claim, **not** on connect — a studio in pre-flight holds no claim and therefore has neither an audience nor a tally of its own. A rebind is published from inside the handshake, before Socket.IO can address the new socket, so the connect handler re-seeds a studio that already holds the claim. What *is* sent unconditionally on connect is the handover snapshot, so a studio can tell an empty window from one it has not heard, and `useSocket`'s `reportsKnown` is what the panel withholds on. Every guard is the server's — room membership, a producer existing, and the cooldown — because a reload clears every client-side one; the sheet's own two-minute disable is a courtesy on top. A socket that never joined the channel gets the same `not_found` an unknown slug does, so membership is not probeable.
- There is no compile-time exhaustiveness for socket handlers. Adding an event to `clientToServer` without registering a handler compiles and surfaces at runtime as an immediate `unknown_event` ack. This is the price of per-call registration, not a defect.
- Register handlers with `on(socket, 'event', fn)` from `socket/lib/on.ts`, never `socket.on` directly: `handle` needs the event name for its watchdog log. It is a plain function, not a registry, and the cast inside it is confined to that one line.
- The handshake carries `{ clientVersion, pin, speakerCode?, studioSession? }` and `authorizeHandshake` makes the whole connection-time decision. The schema pairs the last two both ways: a speaker code without a session cannot be honoured, and a listener has no studio to identify. `authorizeHandshake` **takes no claim** — opening a studio is not a request to broadcast, and a colleague arriving to check their microphone must not end a live broadcast. It registers the studio socket and, when the session already holds the claim, rebinds it to this connection. Still synchronous on purpose: better-sqlite3 is, so the code lookup and that rebind cannot interleave with another socket's. `presence.release` on disconnect is the matching half. There is no `channel_busy` and no `displacedSocketId`: a channel has exactly one valid speaker code, so the handshake has nothing to refuse as busy, and a handover never disconnects anybody.
- Event and channel rooms are nested, not alternatives. A listener on the selector is in the event room only; a listener in a channel is in both. Aggregate updates (`channel:status`) fan out to the event room; per-channel signalling goes to the channel room. Membership is re-established in the connect handler rather than the gate, because Socket.IO replays the auth payload on reconnect.
- The broadcast claim lives in memory in `core/presence.ts`, never SQLite: a boolean column drifts from reality on any crash. It is not liveness — it survives a reconnect that liveness does not, and a deliberate end frees it while the studio stays open. `core/handover.ts` beside it holds at most one pending request per channel: `TAKEOVER_AFTER_MS` of 30 000 before the waiter may force a swap, `GRANT_DEADLINE_MS` of 10 000 for a granted studio to produce, an injectable clock and one unref'd timer per channel in the shape of `core/reports.ts`, and `handover-changed` / `handover-granted` notifications. Confirming, forcing, ending the broadcast and departing all reach one `grant`, which is permission to produce and not the claim: the claim moves at `complete`, so a grant that never produces leaves the outgoing interpreter exactly as live as they were. A cancelled grant reaches the media layer through `onGrantCancelled`, a registration point rather than an import, because `core/media` already imports presence and the reverse would close the cycle. Produce is authorised by the claim (`channel_taken` otherwise), taken before the handler's first `await` and released again if that produce fails; a granted produce is held **beside** the standing producer, and the swap window closes when the last listener has left the outgoing producer or at `SWAP_DEADLINE_MS`. A producer a swap replaced closes silently — publishing its close would report an off-air the channel never had.
- Socket validation is asymmetric by rule: the server parses everything arriving from a client; the client trusts the server. Version drift is handled once, at connection time, by the handshake gate.
- The client socket sets `ackTimeout: 10_000` and must never set `retries` — that enables replay, and signalling operations are not idempotent. The server's `HANDLER_TIMEOUT_MS` is 8s, deliberately below the client's ack deadline, so a wedged handler yields a real `timeout` ack.
- The public Socket.IO lifecycle distinguishes `lost` from `connecting`: a retryable disconnect shows `Connection lost`, the manager's `reconnect_attempt` advances it to `Reconnecting…`, and a successful `connect` clears it. A `connect_error` is retryable only while Socket.IO's `socket.active` remains true; a handshake refusal and `io server disconnect` are terminal errors. `LinkState` combines Socket.IO and mediasoup health before `ConnectionLine` renders their one shared status; no public connection toast exists. Its `idle` kind is the screen saying nothing rather than reporting: it is returned only under a connected socket when `mediaWanted` is false — a guest who has not asked for audio, which includes every guest on a channel with no producer — and the line renders empty there, because a socket with no media leg behind it is not a link anyone asked about. `isLinkUp` therefore counts `idle` as up, and broadcast copy gates on that helper rather than on the line's own vocabulary, or a guest idling on a live channel would read `Offline`. The line reserves its slot (`min-h-12`) in every state including `idle`: its four shapes run 17px to 47px tall, so an unreserved slot moves everything below it by 30px the moment audio starts.
- Route paths are declared without the `/api` prefix; the prefix lives in the document's `servers` entry and the server's mount point.
- `packages/contract/openapi.json` and `src/generated/api.d.ts` are generated and committed. `scripts/gen.ts` reads `apps/server/package.json` for `info.version`, which points the contract at its own consumer — accepted, and confined to that script: no file under `packages/contract/src` may do it. Run `pnpm gen` after any schema or route change; CI fails on drift.
- The media layer's settled shape: one router per event and never per channel, because a transport can only consume producers on its own router — that is what makes a guest's language switch a consumer swap rather than a renegotiation. Nothing is piped between routers, so one event is capped at one CPU core; the worker pool exists for crash isolation, not throughput. A room is created by a produce and by nothing else, and torn down after a grace period once it holds no producers and no transports. A worker that cannot start at boot is fatal; one that dies later is not.
- Media state is process memory and is never persisted, so a reconnection and a server restart are indistinguishable to a client: every `connect` discards every held identifier and renegotiates from capabilities. A transport that remains `new`, `connecting` or `disconnected` for five seconds recovers on a ladder: the first attempt restarts ICE on the same mediasoup transport, every later one rebuilds the transport outright, and after four the direction gives up rather than holding a phone's radio awake forever. A transport whose direction has never reached `connected` waits `ICE_FIRST_GATHER_DELAY_MS` instead of five seconds, because cutting a first gather short restarts ICE on candidates the browser has not finished trying; the fact lives on the session per direction, like the attempt count, so a rebuilt transport keeps the short deadline. `failed` skips the restart step and rebuilds immediately — the browser has already proved that path dead, and a restart re-gathers on the same peer connection — and a socket connect always supersedes an attempt in flight. The restart comes first because it is cheap and keeps the consumers or producer attached while fresh ICE credentials recover a changed network path. The rebuild exists because an ICE restart re-gathers on the browser's existing `RTCPeerConnection`, which after a Wi-Fi-to-cellular handoff can be holding the interfaces the device had when it was created — on Android, cellular IPv6 addresses alone, which pair with nothing the IPv4-only server announces, so ICE stays in `new` with no candidate pair and no error anywhere. Chromium keeps that stale network view for the page, so replacement transports inherit it; a full reload creates the fresh view that recovers. At the first five-second snapshot, a receive transport with literal local and offered candidate families that do not overlap and no candidate pairs exposes the listener's `Reconnect` reload immediately while generic recovery continues; hostname or otherwise unknown candidates do not justify that diagnosis, and a single unknown-family remote candidate withholds it outright: that is a name the browser may still resolve, possibly through DNS64 to a family it does have. `media:close-transport` lets the ladder rebuild: the server permits one transport per direction per socket, so the direction has to be released before a fresh one can be created, and the attempt count lives on the session per direction rather than on the transport, or each rebuild would restart the ladder and rebuild forever. The mismatch is addressed at the source by offering both address forms (see the `PUBLIC_ADDRESS` bullet below); a TURN relay remains the answer for a carrier with neither a routable IPv4 path nor NAT64, and it may not be made a requirement an operator has to configure. A speaker records the effective mute state when Socket.IO drops and re-produces with the same `paused` value after reconnect; recovery must never force an unmuted speaker to muted or unmute a speaker who was already muted. The mic target stays live through that outage rather than disabling with the link — `producer.pause()` is local and stops the audio on its own, so an interpreter can always cut a hot mic even while signalling is down, and this deliberately narrows R16's dashed-rim rule to the pre-producer state. Three things follow and are load-bearing together: a failed mute control resolves to **muted** in both directions (`rollbackMutedAfterFailure`), because undoing a pause the interpreter can hear worked is the one failure they cannot see; a mute pressed during the outage rewrites the pending `lastEnd`, which the reconnect re-produces from and which otherwise still holds the state at drop time; and the studio prefers `localMuted` over the server snapshot whenever `isLinkUp` is false, since a snapshot from a dropped socket describes a channel nobody is updating.
- `TRUSTED_PROXY_IPS` is the only environment variable this admin account work adds: optional, comma-separated, unset by default.
- `DATA_DIR` is the one variable naming user data, and both files that are user data live under it — `linguacast.db` and `admin.json`. Each filename sits with its owner (`db/index.ts` and `core/auth/credentials.ts`); there is no separate variable for the credential file, because recovery is deleting one file in the directory the operator already mounts. `MEDIA_STUN_URL` carries a public default rather than being optional: a deployment shipping without STUN fails for exactly the guests least able to diagnose it. Empty means off, which is why it parses as a defaulted string trimmed to `undefined` rather than as `.optional()`.
- The media environment variables are `PUBLIC_ADDRESS`, `MEDIA_LISTEN_IP`, `MEDIA_RTC_PORT_BASE`, `MEDIA_MAX_WORKERS`, `MEDIA_ROOM_IDLE_GRACE_MS` and the optional `MEDIA_STUN_URL` / `MEDIA_TURN_URL` / `MEDIA_TURN_SECRET`. Worker *i* binds one port at base + *i*, on UDP and TCP alike, so the operator forwards a fixed number of ports that does not vary with audience size. `PUBLIC_ADDRESS` is required in production and has no safe default — a wrong one yields well-formed ICE candidates nobody can reach and errors nowhere, which is why the startup summary names both it and the address it resolved to. It is named for the operator's concept, not the protocol's: it carries no `MEDIA_` prefix because the question it answers is "where is this server", and operator-facing text (`.env.example`, `docs/hosting.md`, every boot log and error) must never say "announced address" or "ICE candidate" at them. Internally the value stays `announcedIp`, which is what it is once it reaches mediasoup. TURN takes a shared secret and credentials are minted per session; a standing credential handed to every guest is an open relay.
- `PUBLIC_ADDRESS` is announced verbatim, hostname and all, and `core/media/announced-address.ts` resolves it to an IPv4 address at boot — fatally if it cannot, and equally fatally if the name answers only with private or loopback addresses, which under split-horizon DNS inside a container is the same silent failure wearing a different hat — and re-resolves it every minute. `createTransport` then hands the client **both** forms: `augmentCandidates` in `config.ts` derives a literal-addressed twin of every candidate, mirroring its protocol, port and TCP type, with its own foundation and a priority lifted clear of every hostname candidate so the literal is tried first — one step above each source would tie the TCP twin with the UDP name, since mediasoup gives a worker's two candidates adjacent priorities. One field cannot serve both browsers — Firefox discards a remote ICE candidate naming a host (Mozilla bug 1713128) and mediasoup is ice-lite, so it never sends the check that would form a peer-reflexive candidate instead, while a phone on an IPv6-only carrier reaches the server only by resolving the name through DNS64 to a NAT64 address — so both are offered rather than one chosen. Where `PUBLIC_ADDRESS` is already a literal the list is byte-identical to one form. The resolver returns the whole answer set rather than one address: the address in use is kept while the name still answers with it, so a record with several A entries is not read as a move on every poll, and a refresh that returns nothing routable is treated as a failed lookup rather than an address change. Only one refresh runs at a time. Because the announced value is the configured one, it never moves: a polled change rebuilds no `WebRtcServer`, drops no room and evicts nobody — it re-runs the STUN cross-check, and the next transport created carries the new literal. Recovering an in-flight client path is that client's own ICE recovery, and `media:reset` has no `address_changed` reason. Reasoning: `docs/solutions/integration-issues/announce-a-resolved-address-because-firefox-drops-hostname-ice-candidates.md`.
- Release versions have two independent sources: `apps/server/package.json` owns server plus bundled web, and `apps/mobile/package.json` owns mobile plus Expo's store-facing version (`app.config.ts` derives it; `app.json` must not mirror it). Root, web, contract, client-core and tooling manifests stay private at `0.0.0`. `pnpm version:server [X.Y.Z]` updates server manifest, `.env.example` and generated OpenAPI artifacts; `pnpm version:mobile [X.Y.Z]` updates mobile manifest. Omit argument for an interactive prompt and preview. Neither command commits, tags or publishes. `pnpm version:check` catches drift and runs inside `pnpm check`. Stable tags are `server-vX.Y.Z` and `mobile-vX.Y.Z`; their separate workflows validate exact manifest match and create separate GitHub Releases. Web handshake must equal server version exactly. `clientType` is **defaulted** to `web` rather than required, and a handshake that declares none is answered with the legacy `client_too_old` rather than `web_version_mismatch`: a tab holding a bundle from before that field existed carries its own copy of `socketMessage`, which maps only the old code to the reload message, so the default alone would get it past schema parsing and still print a generic connection failure. Both the default and the old code go once no bundle predating server 0.4.0 can still be open. Mobile handshake carries mobile version and the server enforces `MIN_MOBILE_VERSION`. That floor rises with a server release whenever an older client would be left broken rather than merely behind: it moved to 0.3.0 because a listener that ignores `ChannelStatus`'s producer ids sits on a dead consumer after a handover swap instead of following it. Two hand-written floors decide whether a released client and a released server may talk — `MIN_SERVER_VERSION` in `packages/client-core/src/server/compatibility.ts` and `MIN_MOBILE_VERSION` in `apps/server/src/version.ts` — and `version:check` asserts neither has passed its own track's version, because nothing else notices. `MIN_SERVER_VERSION` is policy and `SERVER_CAPABILITIES` is feature selection: they hold the same value today and must stay separate constants, or the first capability added at a later version silently raises the floor and locks out servers that are otherwise fine. Reasoning, the compatibility matrix and the release runbook are tracked in `docs/versioning.md` and the `release` skill; keep both current with this bullet.
- Node 24 (active LTS), pinned in `.nvmrc` and floored by `engines.node`. Stay on LTS: mediasoup is a native addon.
- `core/media/reflexive-address.ts` asks a STUN server what it sees this host as, once at boot, and warns when that disagrees with the announced address. It is a cross-check and never a source: a binding request reports where *outbound* traffic exits, which legitimately differs from where guests arrive behind a multi-WAN router, CGNAT, or a proxy on another host — so auto-discovering the announced address from it would replace a loud boot failure with the same silent unreachable-candidate deployment the announced address exists to prevent. The probe is fire-and-forget (nothing awaits a third party during boot), skipped when the address is already known unroutable, and off unless `probeReflexiveAddress` is passed, which only `index.ts` does — a test must never send a datagram. It is also the sole subscriber to `AnnouncedAddress.onChange`, which now re-probes rather than rebuilding anything. It binds an ephemeral port because the RTC ports are held, so only the address is ever compared; under endpoint-dependent mapping the port would differ from a worker's while the address still matches.
- `Dockerfile`, `.dockerignore`, `compose.yaml`, `.env.example`, `docker/entrypoint.sh` and `.github/workflows/server-release.yml` are the deployment artifact; `docs/hosting.md` is its operator-facing half. It is named for its track, beside `mobile-release.yml`: it is the only workflow that publishes an image, and the mobile track publishes none. The image compiles once on `$BUILDPLATFORM` — the bundle and the SPA are architecture-independent — and installs only the two tsdown externals per `$TARGETPLATFORM` from the manifest `scripts/emit-runtime-manifest.mjs` generates. The mediasoup worker is fetched explicitly there against a pinned `MEDIASOUP_WORKER_KERNEL`, not left to the postinstall: that names its asset after the *installing* host's kernel major, and each asset targets that kernel's era of glibc — the kernel7 build needs glibc 2.38 and will not load on bookworm, so an image's worker would otherwise depend on which machine built it. Exit status 41 is mediasoup's own signal that a prebuilt binary ran, which is why the build asserts on it. The entrypoint owns `/data` and drops privileges with `setpriv` (util-linux, already in the base) unless Docker's own `user:` directive already made it unprivileged. RTC ports are published one-to-one: a remapped port leaves signalling working and audio silently absent, because the port inside the ICE candidate is the one the worker bound. Reasoning for the pinned worker: `docs/solutions/integration-issues/pin-mediasoups-prebuilt-worker-to-a-kernel-line-the-base-image-can-load.md`. Every operator-facing setting lives in `.env.example` and nowhere else, and only a line the operator must actually decide is left uncommented there — `PUBLIC_ADDRESS` and `TRUSTED_PROXY_IPS`, plus `LINGUACAST_VERSION` because Compose interpolates it. A variable at its default is commented out, so the file reads as a list of decisions rather than a list of values — `compose.yaml` reads it through `env_file` and interpolates `LINGUACAST_VERSION` into the image tag, so an upgrade is one edited line rather than a second place to keep in sync. `PUBLIC_ADDRESS` is declared a second time under `environment:` only for its `:?` guard, which fails `docker compose up` by name before a container exists.
- Commands: `pnpm dev` (contract's gen watcher, the server on 3000 under `tsx watch`, Vite on 5173 proxying `/api` to 3000), `pnpm gen`, `pnpm build` (contract gen → web build → server build, itself `tsdown` plus `scripts/copy-migrations.mjs`, then web's `dist` copied into `apps/server/dist/public`), `pnpm typecheck`, `pnpm check`, `pnpm test`. `pnpm test` at the root now covers four Vitest packages — the server, the web app, the contract and `packages/client-core` — plus `jest-expo`; a workspace package that declares no matching script is silently skipped by `pnpm -r`, which is why the shared package carries its own `typecheck` and `test`. `pnpm dev` deliberately does not start Metro — see the `apps/mobile` bullet — and `pnpm test` runs Vitest and `jest-expo` both. `pnpm typecheck` runs `pnpm gen` first, so a clean `git status` after it *is* the generated-file drift check CI enforces — there is no separate drift command.
- `apps/web`'s test suite is pure-helper only: `vitest.config.ts` there sets the `@` alias and nothing else, with no jsdom and no component rendering, and it does not reuse `vite.config.ts`. A test that needs to render a component is a signal to reconsider the test, not to add jsdom. Tests import `describe`/`it`/`expect` from `vitest` explicitly; do not enable `globals`, which would require `vitest/globals` in a `types` array and break `packages/contract`'s `"types": []`. `*.test-d.ts` files hold compile-time type assertions checked by `pnpm typecheck`, not by Vitest.

## Product context

- Both web studio screens share `StudioChrome` (the event name lives there and nowhere else) and `StudioTitle` (centred badge above the channel `h1`). From `lg`, on air is two columns: a stage, sticky only on a window at least 45rem tall so End broadcast is never held below the fold, (title, mute target, connection line, End broadcast, listener page link) and one panel list in DOM order (screen-awake chip, listener reports, stats, input level, audio settings). A new panel is one line appended to that list — no `order-*` classes and no per-breakpoint grid. Below `lg`, the stage comes first, the panels follow, and End broadcast with the listener link sits at the page foot so it is never directly under the mute target. End broadcast and the link are rendered twice, one copy per breakpoint hidden with `display: none`, rather than reordered with CSS: a reordered single copy would put End broadcast beside the mute target in tab order while showing it at the bottom. `ListenerReports` mounts only while it has reports, a recent resolution, or a tally that has stayed unknown for two seconds, at every size — the grace keeps a go-live or reconnect from mounting and unmounting it, which would move every panel below. Its announcements come from an `sr-only` live region that stays mounted, as do pre-flight's colleague alert and checking note: a region that mounts already holding its text is not announced.

- The web on-air studio holds a screen wake lock for the whole life of `SpeakerOnAir` — mount and unmount are already exactly the on-air window, so nothing keys on `BroadcastState` — through `lib/use-screen-wake-lock.ts`. Every call is best effort in the shape `lib/audio/use-listener-media-session.ts` uses: an absent `navigator.wakeLock`, a refused request and a refused release throw nothing and surface nothing beyond the status the hook returns. A browser drops the lock when the document hides, so a fresh one is taken on `visibilitychange` back to visible. The lock runs on every platform; only the guidance is gated, to phones and tablets alike — `isHandheldBrowser` reads iPadOS's touch count because that browser reports a desktop Safari user agent and is otherwise indistinguishable from a Mac. `ScreenAwakeNotice` is a separate component precisely so the hook does not inherit that gate: on a handheld it renders a chip whose dialog explains that a phone takes the microphone away when the browser backgrounds or the screen locks. The chip reports that outcome, and the three labels in `lib/screen-awake-copy.ts` are three different sentences rather than one string doing several jobs: a granted lock is a status (`Keeping the screen awake`), an unsupported or refused one is a warning (`Screen may dim`), and only the tick before the first request settles carries the bare instruction. The dialog states the microphone warning in every one of those states, because that is the half which survives a lock the browser never granted, and nothing about the dialog is stored. `lib/phone-browser.ts` holds both predicates: `isPhoneBrowser`, which the guest app notice uses and which excludes tablets, and `isHandheldBrowser`, which this chip uses and does not.

- Mobile's `ListenTarget` shows a native loading spinner during the listener's `holding` grace period, keeps the target at full opacity, and disables taps while exposing its busy state to accessibility services, matching the web target's waiting behavior.

LinguaCast is a self-hosted, open-source simultaneous-interpretation platform for live in-person events; low audio latency is the core requirement. It targets one modest server run by a church or educational institution, a handful of concurrent events, and tens to low hundreds of listeners. Prefer simple operation over scale; horizontal scaling, multi-tenancy, sharding, and cloud-managed dependencies are out of scope.

There is one authenticated Admin. Events own Channels; an Event PIN grants listening, while a per-Channel Speaker code grants broadcasting. Speakers and listeners have no accounts: possession of the link or code is the entire authorization. Preserve that property and question features that appear to need listener identity. `CONCEPTS.md` is the authoritative domain vocabulary.

The server is Node.js with Socket.IO, SQLite/Drizzle, and the audio-only mediasoup SFU; the current client is a React SPA. Expo/React Native is planned, so keep the API portable beyond browsers.

## Working in this repo

Mobile appearance uses device-local SQLite key-value storage, as documented above. Storage for other settings remains open. Record further decisions here rather than leaving them implicit in code.

Source comments must not depend on gitignored local plan, requirement, decision, brainstorm, or design-turn identifiers. State the rationale self-contained or link to tracked durable documentation such as `docs/solutions`.

What is left on mobile is the **speaker studio**, and nothing before it. Deferred with reasons rather than forgotten: moving `src/media/transport.ts`, `device.ts` and `diagnostics.ts` into `packages/client-core`, which becomes worth doing once a second mediasoup shell exists to shape the seam against; an app-drawn list of output devices, which neither platform offers; and replacing the web app's silent-WAV Media Session carrier, which this work does not touch. `apps/mobile` sets `reactCompiler: true` while `apps/web` runs no compiler plugin, so a hook consumed as source from `packages/client-core` is auto-memoized on one platform and not the other — the asymmetry is accepted rather than removed, because excluding the package would opt the app's own hooks out of a setting it deliberately turned on. App icon, splash screen, store metadata, EAS configuration and store build/submission automation are deferred; `mobile-v*` CI already validates the source release and creates its separate GitHub Release. Scanner's camera path has no simulator substitute — it needs a device and a printed code. The app claims `open.linguacast.app` through iOS associated domains and Android verified intent filters. `app/+native-intent.tsx` unwraps its `url` query parameter through `parseListenerLink` and the existing route builders, with malformed links returning Home. The external host must publish Apple and Android association files before the claim works; deploying that host and store fallback is separate work. Native configuration changes require a dev client rebuild. Direct links to self-hosted origins still use link entry or scanning.

Non-blocking follow-ups: a coturn/TURN relay deployment and automated `/data` backup (packaging itself is done — see the Dockerfile bullet above), and a pre-flight "someone is waiting" signal. That last signal requires channel-room membership and a new concept; do not relax the meaning of `Listening`, because a guest waiting on an offline Channel allocates nothing server-side.

`docs/` is local-only scratch — plans, design handoffs and `docs/superpowers` are gitignored on purpose. Never stage them and don't "fix" their absence from git. There are three exceptions, each with its own `.gitignore` negation: `docs/solutions`, solutions to past problems filed by category with YAML frontmatter (`module`, `tags`, `problem_type`), which you should read when working in an area it covers; `docs/hosting.md`, the operator-facing hosting guide; and `docs/versioning.md`, the release and compatibility contract. `.claude/skills` is tracked on the same terms — `release` is the procedure for cutting either track, and `docs/versioning.md` is the reasoning behind it, so a change to one usually means a change to the other. `.claude/settings.local.json` stays local.
