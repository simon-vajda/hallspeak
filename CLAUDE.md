# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

Specs A through E are implemented: a pnpm workspace with `packages/contract`, `tools/openapi-codegen`, an API-only-plus-SPA `apps/server`, `apps/web`, a typed Zod-validated Socket.IO signalling transport, and a SQLite persistence layer. Spec E adds the `events`/`channels` schema, the public listener/speaker API, unguarded admin CRUD, PIN rate limiting, and the socket connection lifecycle (handshake authorization, event/channel rooms, speaker presence). The design system has landed: `apps/web` carries the handoff's light and dark token blocks, Space Grotesk, and a 20px card radius. The Home route `/` and **both admin routes** are built to the design — the admin screens manage events and channels end to end (create, edit, enable, delete, regenerate a PIN or a speaker code, copy the share links, and a client-generated QR for the listener URL) and remain **unauthenticated**, like the API behind them. **The guest and speaker routes are still deliberately skeletal** — real routes, real data fetching, real socket wiring, placeholder markup — and simply inherit the tokens until they are redesigned in turn. There is no mediasoup and no audio yet: the interpretation features themselves are still intended design, not existing implementation. Keep this file current as decisions are made.

## Layout and commands

- `packages/contract` — hand-written Zod schemas and `createRoute()` definitions. **Never built:** every export points at TypeScript source, and consumers compile it. `src/socket` holds the socket event contract behind the `./socket` subpath export — event definitions as data, with Socket.IO's generic event maps derived from them by inference. It is **not** re-exported from the root barrel, which pulls in Hono via `./openapi`; browser clients import `@linguacast/contract/socket`. `./patterns` exists for the same reason and on the same terms: `src/schemas/patterns.ts` holds the bare regexes (`PIN_PATTERN`, `SLUG_PATTERN`, `SEMVER_PATTERN`) with no zod and no Hono, so the web app can share the protocol's shapes without either reaching its bundle — importing them from the root barrel or `./schemas` would. The contract imports neither `socket.io` nor mediasoup. Its tsconfig sets `"types": []` with no DOM on purpose (the React Native seam) — a `node:`/DOM import in `src` must fail to compile there.
- `tools/openapi-codegen` — a private workspace package whose only job is holding `typescript@5.9.3`. `openapi-typescript` emits its output with the `ts.factory` AST API, which TypeScript 7.0 does not expose (a programmatic API returns in 7.1). The package exposes an `openapi-codegen` bin that runs openapi-typescript's own CLI in-process from its TypeScript 5 resolution scope, and `packages/contract` depends on it — so the arrow points `contract → openapi-codegen` and the tool knows nothing about the contract's layout. TypeScript 5 therefore appears in exactly one `package.json` and is not reachable as a binary from any package that compiles source; `pnpm why -r typescript` is the mechanical form of that invariant. Every real package pins `typescript@7.0.2`. **Exit condition:** when TypeScript 7.1 ships its programmatic API and `openapi-typescript` adopts it, delete `tools/` and move `openapi-typescript` into `contract`'s devDependencies.
- `apps/server` — Hono + `@hono/zod-openapi`. `app.ts` builds the app without listening; `index.ts` owns the listener. `lib/problem.ts` stays transport-agnostic so the signalling layer can reuse it. `defaultHook` must be passed to *every* `OpenAPIHono` instance that registers routes — it is not inherited by sub-apps.
- `apps/web` — Vite 8 + React 19 SPA. TanStack Router with **file-based** routing: a file under `src/routes/` *is* a route, and the Vite plugin regenerates `src/routeTree.gen.ts` on dev-server startup and on every change there. Routes are nested as **directories, not dotted filenames** — `routes/admin/events/$id.tsx`, not `routes/admin.events.$id.tsx` — and a directory's layout route is its `route.tsx`. That file is generated **and committed** (typechecking runs before any build) but has no drift tripwire — a stale route tree is immediately visible as a missing page, unlike a stale `api.d.ts`. It is excluded from Biome. `src/components/ui` is the shadcn CLI's target: add and update components by re-running `pnpm dlx shadcn@latest add <name>` from `apps/web`, then `pnpm check:fix` (the CLI's formatting differs from Biome's). Deliberate customisations **are** allowed there — shadcn's model is that the scaffolded code is yours — but each one must be **recorded here**, because a later `add` of that same component silently drops it. Current customisations: **`button.tsx` carries a `pill` size** (`h-12 rounded-full px-6 text-base font-semibold`), the design system's primary action, and **`switch.tsx` carries an `lg` size** (46×27 with a 21px thumb — the admin enable switch as drawn, and the only size that clears the handoff's 44px hit target); re-running `shadcn add` for either component removes them. Prefer call-site classes for one-off styling and reserve edits for things that belong to the component itself. `biome.json` turns six lint rules **off for that directory only** (four `a11y`, `noArrayIndexKey`, `noDoubleEquals`): upstream shadcn trips them by design — `role="group"` on a div, a `Label` primitive with no control — and hand-fixing generated files just means the next `add` reintroduces the error. Formatting still applies, which is why `check:fix` follows every CLI run. `tsconfig.json` must **not** declare `baseUrl` — TypeScript 7 removed the option; `paths` alone resolves for both `tsc` and the shadcn CLI. `src/api`, `src/signal`, and `src/state` are the portable directories that lift into `packages/client-core` when the Expo app begins; **everything else under `apps/web/src` is web-only.** `src/lib/signal.ts` exports `connectSignal(auth)`, **not** a module singleton: the handshake carries the event's PIN, so one socket per page is required — a singleton could not serve two events and would be rejected outright on the home page, which has no PIN.
- **The design's off-scale values go on the Tailwind scale, not into arbitrary utilities.** Tailwind v4 derives the whole spacing scale from `--spacing`, so 26px is `6.5`, 18px is `4.5` and 1120px is `280` — `px-[26px]` is never the right answer. Two values are *semantic* enough to be named in `index.css`: `--spacing-gutter` (the 26px screen gutter, `px-10` from `lg`) and `--spacing-shell` (the 1120px admin cap). The handoff's type ramp is four `--text-*` entries — `text-screen`, `text-section`, `text-label`, `text-meta` — each carrying its own weight and tracking, so a call site names the step instead of re-stating three properties; body text is Tailwind's own `text-sm`. Arbitrary values remain right for one-off type sizes and grid templates.
- **`src/components/admin` holds the admin screens' composite components** — the dialogs, the channel row, the chip list, the PIN card — deliberately *outside* `components/ui`, which the shadcn CLI overwrites. None of it is a candidate for `packages/client-core`; it is web-only. The two admin surfaces never use `live`, `live-muted` or `live-foreground`: liveness is not modelled yet, so the design's status column, channel pill and pulse dot all express **enabled** instead, the dot is dropped rather than recoloured, and an enable switch's checked track is `foreground` — borrowing `live` or `primary` to mean "enabled" would reintroduce the exact ambiguity the palette was rebuilt to remove. The events table is a list of CSS-grid rows rather than a `<table>`: the design's `fr` columns need grid, and every cell is self-describing, so the column headings are decorative — which is why there is no `components/ui/table.tsx`.
- `apps/server/src/db` — better-sqlite3 + Drizzle. `client.ts` holds the `createDb(path)` factory and **must stay free of import side effects**; `index.ts` holds the `db` singleton and opens a file at module scope. `testing.ts` imports the factory, never the singleton — otherwise loading the test helper would provision `./data/linguacast.db` on every test run. Handlers `import { db }`; there is no dependency injection and none is wanted.
- **Migrations are generated, reviewed and committed** under `src/db/migrations`. Run `pnpm -F @linguacast/server db:generate` after any change to `schema.ts`, read the SQL, commit it. `drizzle-kit push` is rejected — it leaves nothing in git and makes upgrades irreproducible. There is deliberately **no `db:migrate` script**: `runMigrations(db)` runs in `index.ts` before `serve()`, so the process either has a current schema or fails to start, and the operator's upgrade procedure is "pull and restart".
- **`migrate.ts` resolves its folder against `import.meta.dirname`; `DATABASE_PATH` resolves against the working directory.** The opposite rules are deliberate: migrations are a build artifact and travel with the bundle (`scripts/copy-migrations.mjs` places them at `dist/migrations`), whereas the database is user data and would be destroyed by every redeploy if it lived in `dist/`.
- **The four pragmas in `createDb` are all non-defaults**, and `foreign_keys` is **per-connection** — unset, constraints are silently inert, which is why it carries a test rather than trust. `data/` is gitignored, so `mkdirSync` in the factory is what makes the first `pnpm dev` on a fresh clone work; its absence is a first-run-only bug, invisible on any machine that already has the directory.
- **`better-sqlite3` is listed as `false` in `pnpm-workspace.yaml`'s `allowBuilds`.** It has no install script, but its `binding.gyp` makes pnpm infer a `node-gyp rebuild` and exit 1 on `[ERR_PNPM_IGNORED_BUILDS]`. Declining the build is correct: the tarball ships prebuilt N-API binaries for all eight platform/libc targets, ABI-stable across Node 22/24/26. Do not run `pnpm approve-builds` for it. `apps/server/src/db/migrations` is excluded from Biome — drizzle-kit rewrites its JSON metadata without a trailing newline on every generate.
- **`drizzle-zod` is deliberately absent.** Row types come from `$inferSelect` / `$inferInsert`. Beyond types it would only add runtime validation of rows, which the contract's wire schemas already cover at the boundary — and it makes deriving API schemas *from tables* easy, which is the inversion ADR §5 rules out. A row is not a DTO.
- **The domain tables are `events` and `channels`.** Both default to **disabled** — enabling is the deliberate act that opens the doors, and it doubles as both "not yet" and "over", so there is no lifecycle column. `pin` and `speaker_code` are regenerable natural keys and therefore **never** primary keys: the row must survive its own code changing. A channel's `slug` is immutable after creation (renaming it would break every printed QR code) and is unique only *within* its event, via the composite `channels_event_id_slug_unique`. The throwaway `meta` table is gone, dropped by migration `0001`; its `0000` migration stays in history rather than being rewritten.
- **The admin events list returns each event with its channels**, not a bare event. It is the only consumer of that endpoint and its chips need every event's channels, so a `listChannels` per event beats a waterfall of one request per row — a deliberate simplicity-over-scalability call at this deployment's scale, not an accidental N+1.
- **404 parity is a rule, not a convention.** A disabled event, a disabled channel and a nonexistent PIN must produce byte-identical responses — any difference tells a scanner which PINs are real. Enforced by a test in `routes/events.test.ts`. The channel lookup checks existence *before* the speaker code for the same reason: a valid code on a disabled channel still 404s and never confirms the code was right.
- **Failed public lookups are rate limited** by an in-memory per-IP token bucket (burst 20, refill 1/s) with a smaller global budget behind it for botnets. Charged on **404 responses only**, so a room full of guests never feels it and only a caller that is guessing pays. It throttles, never bans: two hundred people in a room share one NAT address. In-memory state is correct precisely because the deployment target is one process.
- **`apps/server/src/testing/api.ts` sets `DATABASE_PATH` before *dynamically* importing `../db`.** `env.ts` parses `process.env` at module load and `db/index.ts` opens a file at module scope, so a static import would provision the real `./data/linguacast.db` as a side effect of running the tests.
- The socket endpoint is `path: '/api/socket.io'` on the **default namespace** — a path, not a namespace. All dynamic traffic then sits under `/api`, so one Vite proxy rule and one reverse-proxy rule cover both the API and the socket. Socket.IO attaches at the `http.Server` level and intercepts that path **before Hono sees it**, which is invisible from `app.ts`.
- **There is no compile-time exhaustiveness for socket handlers.** Adding an event to `clientToServer` without registering a handler compiles; it surfaces at runtime as an immediate `unknown_event` ack from the validation middleware, in development. This is the deliberate price of per-call registration — a handler registry would buy exhaustiveness at the cost of per-feature module boundaries and of having `socket` in scope for rooms and disconnect. It is not a defect.
- Register handlers with `on(socket, 'event', fn)` from `src/signal`, never `socket.on` directly: `handle` needs the event name for its watchdog log, and `on` passes it through so the call site names the event once. It is a plain function, not a registry. The cast inside it is confined to that one line — `socket.on` types its listener as a conditional over the event name that TypeScript cannot reduce while the key is still generic; the exported signature is what pins payload and return type to the event's schemas.
- **The handshake carries `{ clientVersion, pin, speakerCode? }`** and `authorizeHandshake` makes the whole connection-time decision. It is **synchronous on purpose**: better-sqlite3 is, so the "is this channel busy" check and the presence claim that follows cannot interleave with another socket's. That is also why the function has a side effect on its success path — it *claims* the channel. `presence.release` on disconnect is the matching half, and the only one. First connection wins; a latecomer gets `channel_busy` and the incumbent is never disturbed.
- **Event and channel rooms are nested, not alternatives.** A listener on the selector is in the event room only and still gets liveness updates; a listener in a channel is in both. Aggregate updates (`channel:status`) fan out to the **event** room so the selector and every channel page agree; per-channel signalling goes to the channel room. Membership is re-established in the connect handler rather than the gate, because Socket.IO replays the auth payload on reconnect and nothing is sticky across connections.
- **Speaker presence is in memory and is a placeholder.** `signal/presence.ts` holds it, never SQLite: a boolean column drifts from reality on any crash and then needs reconciliation to repair a fact the socket layer already knows. `isOnline` currently means "a socket is connected", which is **not** the same as audio flowing — it must be replaced by mediasoup transport state. The comment in that file is the marker; the UI, the broadcast and the client subscription all survive the swap.
- Socket validation is **asymmetric by rule**: the server parses everything arriving from a client; the client trusts the server. Version drift is handled once, at connection time, by the handshake gate — re-parsing every inbound message would turn a clear `client_too_old` rejection into a scatter of per-message parse errors.
- The client socket sets `ackTimeout: 10_000` and **must never set `retries`** — that enables replay, and signalling operations are not idempotent. The server's `HANDLER_TIMEOUT_MS` is 8s, deliberately below the client's ack deadline, so a wedged handler yields a real `timeout` ack instead of an unexplained client-side timeout.
- Route paths are declared **without** the `/api` prefix; the prefix lives in the document's `servers` entry and the server's mount point.
- `packages/contract/openapi.json` and `src/generated/api.d.ts` are generated **and committed**. Run `pnpm gen` after any schema or route change; CI fails on drift.
- Node **24** (active LTS), pinned in `.nvmrc` and floored by `engines.node`. Deliberately LTS rather than Current: mediasoup is a native addon and those track LTS releases far more reliably.
- Commands: `pnpm dev` (three processes — contract's gen watcher, the server on 3000 under `tsx watch`, Vite on 5173 proxying `/api` to 3000), `pnpm gen`, `pnpm build` (contract gen → web build → server build, itself `tsdown` plus `scripts/copy-migrations.mjs` → copy web's `dist` into `apps/server/dist/public`, producing a single bundle that serves both the API and the SPA), `pnpm typecheck`, `pnpm check`. `pnpm test` runs Vitest via `pnpm -r test` in `packages/contract` and `apps/server` — it is no longer a no-op. Tests import `describe`/`it`/`expect` from `vitest` explicitly; do **not** enable `globals`, which would require adding `vitest/globals` to a `types` array and break `packages/contract`'s `"types": []`. `*.test-d.ts` files hold compile-time type assertions checked by `pnpm typecheck`, not by Vitest.
- `@hono/zod-openapi` is pinned to exactly `1.4.0`. Do not float it: 1.5.x has broken type declarations that silently degrade every schema type to `any` under `skipLibCheck`, voiding the handler/contract compile-time guarantee.

## What LinguaCast is

A self-hosted, open-source platform for simultaneous interpretation at live in-person events — church sermons, international conferences, talks. An interpreter speaks into their phone or laptop; guests in the room listen live on their own devices. Low audio latency is the core product requirement.

## Deployment context (drives most design decisions)

Deployed on small servers run by churches and educational institutions, not in a central cloud. Expected load: a handful of concurrent events, listeners in the tens to low hundreds. **Optimize for simplicity of operation and setup over scalability.** Horizontal scaling, multi-tenancy, sharding, and cloud-managed dependencies are explicitly out of scope. A single-process server that an admin can run on modest hardware is the target.

## Domain model

- **Admin** — the only authenticated account in the system. Single user. Creates and edits events, manages app settings, shares links.
- **Event** — e.g. "Sunday Service". Owns one or more channels.
- **Channel** — typically a target language, e.g. "English", "Spanish". One speaker, many listeners.
- **Speaker code** — generated per **channel**, not per event, and grants broadcasting on that one channel only. The speaker link is the ordinary channel URL plus `?speaker_code=…`, so dropping the query param degrades it into a valid listener URL.
- **PIN** — generated per **event**. Six digits, grants listening, and is what a guest types or a QR code carries.
- **Listener link / QR code** — takes a guest directly to an event; they pick a channel and listen.

## Access model

Only the admin authenticates. Speakers and listeners are authorized purely by possession of their link/code — no accounts, no signup, no login. This is deliberate: the friction of authentication would defeat the product. Admin sets up, shares two links, everyone starts using it. Preserve this property when designing new features; if something seems to need listener identity, question the requirement first.

## Intended stack

- **Server** — Node.js with Socket.IO for signalling and SQLite (better-sqlite3 + Drizzle) for persistence, both implemented, and [mediasoup](https://mediasoup.org/) as the WebRTC SFU (not started). Audio-only.
- **Web frontend** — React SPA. This is the only client for now.
- **Mobile** — likely Expo / React Native, planned but not started. Avoid decisions that would lock the API to a browser-only client.

## Working in this repo

The signalling transport (Spec C), the persistence layer (Spec D) and the domain schema, routing and connection lifecycle (Spec E) are settled. Still open: the mediasoup event set and the room/transport/producer lifecycle, settings storage, and admin authentication — which lands as one middleware on the `/admin` subtree, which is why that prefix exists. When those are settled, record them here rather than leaving them implicit in code. The admin UI now exists but shows no on-air state and no listener counts; presence today means only "a socket is connected", and the chip and status positions those screens already carry are where both land once it means "audio is flowing".

`docs/superpowers` is gitignored on purpose — it is local-only scratch material, not part of the repo. Never stage or commit it, and don't "fix" its absence from git.
